AI/ML IMPLEMENTATION PLAN FOR HONEYPOT (LAYER-WISE + GRAPHICAL)
Date: 2026-03-11
Project: t:\honey

====================================================================
1) OBJECTIVE
====================================================================
Build an AI/ML-driven detection and response pipeline for your honeypot
that can:
- Detect unknown/novel attacker behavior (anomaly detection)
- Classify known attack patterns (supervised learning)
- Score risk with explainable reasoning
- Trigger controlled automated responses
- Continuously improve through analyst feedback


====================================================================
2) LAYER-WISE ARCHITECTURE (DETAILED)
====================================================================

LAYER 1: DATA FOUNDATION (Instrumentation + Schema)
----------------------------------------------------
Purpose:
- Collect consistent, high-quality data from all honeypot protocols.

What to implement:
- Unified event schema across SSH/FTP/HTTP/Telnet/SMB:
  event_id, timestamp, src_ip, src_port, dest_ip, dest_port,
  protocol, username, command_or_payload, auth_result,
  bytes_in, bytes_out, session_id, session_duration,        
  honeypot_type, geo_country, asn, raw_metadata.
- Session correlation:
  link all events from same attacker activity using session_id.
- Label readiness:
  add label field: unknown | benign | suspicious | malicious.

Why this is critical:
- In ML systems, data quality is the strongest predictor of model quality.
- Without normalized schema, feature extraction and model training break.

Suggested repo touch points:
- backend/data_collection/models.py
- backend/data_collection/logger.py


LAYER 2: FEATURE ENGINEERING (Signal Extraction)
------------------------------------------------
Purpose:
- Convert raw logs into model-usable numerical and categorical features.

Feature groups:
1. Connection behavior features
   - attempts_per_minute
   - unique_ports_touched
   - failed_auth_ratio
   - avg_session_duration
   - connection_burst_score

2. Credential behavior features
   - username_length
   - username_entropy
   - common_admin_username_flag
   - password_guess_sequence_score (if captured)

3. Command/payload features
   - payload_size
   - suspicious_keyword_count (wget, curl, chmod, nc, powershell)
   - shell_meta_char_density (; | && $() > <)
   - ngram_hash_vector or tf-idf vector (for command strings)

4. Temporal and context features
   - hour_of_day
   - day_of_week
   - inter_arrival_time_mean
   - geo_risk_score
   - ip_reputation_score (if external intel available)

Why this is critical:
- Better features often improve performance more than model complexity.
- Good features reduce false positives and improve explainability.


LAYER 3: MODEL LAYER (Detection Models)
----------------------------------------
Purpose:
- Learn behavior patterns and detect attacks/anomalies.

Recommended phased model strategy:
Phase A (Low label requirement)
- Isolation Forest, One-Class SVM
- Goal: anomaly baseline for unknown attacks

Phase B (When labels become available)
- Random Forest / XGBoost / LightGBM
- Goal: classify known attack families

Phase C (Text-intent understanding)
- Lightweight NLP pipeline over command/payload text
- Goal: detect exploit intent and suspicious command semantics

Output per event/session:
- anomaly_score (0-1)
- class_probabilities (if supervised)
- model_confidence

Why this is critical:
- Honeypots typically start with limited labels; phased growth is practical.


LAYER 4: DECISION + EXPLAINABILITY LAYER
----------------------------------------
Purpose:
- Convert model outputs into analyst-friendly threat decisions.

Threat scoring design (example):
risk_score =
  0.45 * anomaly_score
+ 0.30 * classifier_malicious_prob
+ 0.15 * rule_engine_score
+ 0.10 * reputation_score

Severity mapping:
- 0-24   = LOW
- 25-49  = MEDIUM
- 50-74  = HIGH
- 75-100 = CRITICAL

Explainability payload:
- top_contributing_features
- triggered_rules
- confidence_level
- short textual reason
  Example: "High failed-auth burst + suspicious shell commands"

Why this is critical:
- Security operations require interpretable alerts for triage and action.


LAYER 5: RESPONSE ORCHESTRATION LAYER
-------------------------------------
Purpose:
- Trigger safe, proportional response based on risk.

Response policy examples:
- LOW:
  log only, no action
- MEDIUM:
  create dashboard alert + retain full session trace
- HIGH:
  enrich event (geo/reputation), increase logging granularity,
  optional temporary soft throttle
- CRITICAL:
  isolate interaction channel, trigger urgent notification,
  optional firewall block with TTL and manual override

Why this is critical:
- Detection alone has limited value without operational response.


LAYER 6: HUMAN-IN-THE-LOOP FEEDBACK
------------------------------------
Purpose:
- Continuously improve models and reduce false positives.

What to add:
- Dashboard controls: mark true_positive / false_positive / benign_noise
- Store analyst annotations with timestamp and analyst_id
- Build weekly retraining dataset from reviewed records

Why this is critical:
- Threat behavior evolves; human feedback is your adaptation loop.


LAYER 7: MLOPS + GOVERNANCE LAYER
----------------------------------
Purpose:
- Keep models reliable, auditable, and updatable in production.

Key capabilities:
- Model version registry (v1, v2, ...)
- Drift monitoring (feature distribution shifts)
- Performance tracking (precision, recall, FPR by protocol)
- Rollback strategy if quality degrades
- Retraining cadence (weekly/bi-weekly)

Why this is critical:
- A model that is not monitored will eventually fail silently.

6) PRACTICAL NOTES FOR YOUR CURRENT CODEBASE
====================================================================

- Keep raw event logs immutable for forensic integrity.
- Create separate transformed dataset for model training.
- Start with offline model scoring before real-time blocking.
- Default to safe responses (monitor/enrich) before aggressive blocks.
- Evaluate per protocol; SSH behavior differs from HTTP/SMB.
